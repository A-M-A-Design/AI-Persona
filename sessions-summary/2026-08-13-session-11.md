# Session 11 — 2026-08-13 : le site est en ligne, et ce que le chemin a révélé

Trois PR en squash. **PR #36** (`364b72e`) : la mesure d'audience et le guide de
déploiement. **PR #37** (`6571c37`) : un `.vercelignore`, écrit avant de
déployer et pour une raison précise. **PR #38** (`0b37558`) : les fichiers de
secrets hors `.env`, ignorés des deux côtés.

**Le site répond : https://ama-ai-persona.vercel.app**

Le fil de la session : **la mise en production n'a rien cassé, mais elle a
révélé trois protections qui ne protégeaient pas.** Aucune n'était visible
depuis le code — il a fallu déployer, ou s'apprêter à le faire, pour les voir.

## Ce qui tourne, et comment on le sait

| Vérification | Méthode | Résultat |
| --- | --- | --- |
| Routes publiques | `curl` sur 6 chemins | 200 partout |
| Chat en production | vraie requête, vraie réponse | streaming OK |
| Limite de débit | clé fraîche lue **dans Upstash** | compteur partagé |
| Aperçus de partage | `og:url`, `og:image`, `sitemap.xml` | URL de production |
| Variables | `vercel env ls` | 4 clés × Production **et** Preview |
| Contenu téléversé | arbre du déploiement via l'API | 200 fichiers, rien de sensible |

La ligne qui compte est la troisième. Les journaux auraient pu dire
`[rate-limit] compteur partagé Upstash` sans que rien ne le prouve — un message
n'est qu'une chaîne de caractères. La preuve est ailleurs : après un appel réel
depuis l'extérieur, une clé `ama:chat:jour:<ip publique>` apparaît dans Upstash
avec un TTL neuf. La production écrit dans la base ; ce n'est pas une lecture de
configuration, c'est une trace d'écriture.

La quatrième mérite aussi un mot : `lib/site.ts` déduit l'URL de
`VERCEL_PROJECT_PRODUCTION_URL`. Résultat, **aucune variable à poser** pour que
les aperçus fonctionnent — ils étaient corrects au premier déploiement.

## Trois protections qui ne protégeaient pas

### 1. Le CLI ne connaissait pas le certificat d'entreprise

`vercel login` échouait sur `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. Même cause que
celle qu'adresse `scripts/with-ca.mjs` pour `next` — sauf que ce lanceur ne
couvre que les commandes du projet.

Mesuré des deux côtés plutôt que supposé :

```
sans certificat : ECHEC UNABLE_TO_GET_ISSUER_CERT_LOCALLY
avec            : TLS ok, HTTP 403
```

Le 403 est le bon résultat : la poignée de main passe, l'API répond, elle refuse
seulement une requête non authentifiée. Un premier essai avait donné « Logged
out » avec et sans certificat — sans valeur, `whoami` ne sortant pas sur le
réseau quand aucune session n'existe. C'est le genre de test qui rassure à tort.

### 2. Un `vercel deploy` aurait emporté 31 Mo d'IP Accor

Avant le premier déploiement, la trace de la fonction serveur — mesurée
localement — contenait :

| Fichier | Poids |
| --- | --- |
| `notion arthur.zip` | 22,7 Mo |
| `welds-mcp-v3.zip` | 5,1 Mo |
| `2.2.2_AccorDesignTokens_20261008_1001.zip` | 3,7 Mo |
| `linkedin profil.pdf` | 63 Ko |

Tous sont gitignorés. **Un build déclenché depuis GitHub ne peut pas les voir**,
il ne connaît que le dépôt. Le risque est ailleurs : un `vercel deploy` lancé
depuis un poste téléverse le dossier de travail.

Le CLI honore vraisemblablement `.gitignore`. « Vraisemblablement » est
acceptable pour un fichier de cache, pas pour de l'IP client — d'où
`.vercelignore`, écrit noir sur blanc et valable pour les deux chemins.

Vérification après coup, sur l'arbre réel du déploiement : **aucun `.zip`, aucun
`.pdf`, `styles/welds-src/` monté vide.** Le point délicat était de distinguer
« répertoire vide » de « enfants non retournés par l'API » ; la comparaison avec
ses frères tranche — `components` remonte 7 enfants, `generated` 3, `welds-src`
zéro.

### 3. La protection des secrets ne tenait qu'à `.env*`

Un fichier de codes de récupération Vercel déposé à la racine du projet. Ni
`.gitignore` ni `.vercelignore` ne le couvraient : il est parti dans le
déploiement suivant — présent dans `dpl_5VPSHG…`, absent du précédent.

Il n'était pas servi publiquement (404 sur les trois chemins plausibles), mais
il a bien atterri dans le stockage de source du déploiement.

**Le motif `.env*` suppose que tout secret arrive nommé comme une variable
d'environnement.** C'est faux dès qu'un service livre un bloc de codes à coller
quelque part. La correction retient un motif large — `*recovery-codes*`,
`*backup-codes*`, `/secrets/`, `*.key`, `*.p12`, `*.pfx` — parce que le prochain
fichier s'appellera autrement.

Un redéploiement ramène le compte à 200 fichiers, sans les codes.

## « ashen » ne veut rien dire

L'URL de production s'appelait `ai-persona-ashen.vercel.app`.
`ai-persona.vercel.app` répond 500 : le sous-domaine appartient à un autre
projet, et Vercel complète alors avec un mot tiré de sa liste. Arthur a tranché
pour `ama-ai-persona`.

L'ajout d'un sous-domaine ne suffit pas : `og:url` et `sitemap.xml` sont figés au
build. Il a fallu redéployer pour que les métadonnées suivent. L'ancienne URL
continue de répondre.

## Ce qui reste

- **Régénérer les codes de récupération Vercel** — c'est le seul geste qui rend
  les anciens sans valeur. Idem pour le jeton Upstash, passé par une
  conversation. Les deux sont à répercuter **aux deux endroits** quand ils
  changent : `.env.local` et Vercel, faute de quoi la production bascule
  silencieusement sur le repli en mémoire.
- **Connecter le dépôt GitHub** : `vercel git connect` échoue, l'app GitHub de
  Vercel n'étant pas autorisée sur `A-M-A-Design`. Sans elle, chaque mise en
  ligne reste un `vercel deploy` manuel.
- **Supprimer `dpl_5VPSHG…`**, périmé mais porteur du fichier de codes.
- **Trancher l'indexation.** `robots.txt` autorise l'indexation et le sitemap
  déclare des URLs en `.vercel.app`. Si elles sont indexées avant l'achat du
  domaine, il restera des URLs mortes à rediriger.
- **Deux avertissements Turbopack** sur `lib/article-body.ts` (« Dynamic
  filesystem access causes tracing of the whole project ») : c'est ce qui élargit
  la trace. Sur Vercel le total plafonne à ~7 Mo, très en deçà des limites —
  non bloquant, mais la cause est identifiée.
