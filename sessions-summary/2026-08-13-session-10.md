# Session 10 — 2026-08-13 : les composants nous appartiennent, et le site s'écoute

Quatre PR en squash. **PR #28** (`ab91be4`) : la réécriture des
composants WDS sur le préfixe `ama`, qui coupe la dernière dépendance du build à
l'IP Accor. **PR #29** (`eb7ba39`) : huit correctifs d'accessibilité, tous nés
d'une passe au lecteur d'écran menée par Arthur, et l'audit qui les outille.
**PR #31** (`5f83c95`) : les trois arbitrages restés en attente, APCA mesuré en
parallèle, et la limite de l'outillage enfin résorbée. **PR #32** : la
documentation remise d'aplomb, à commencer par un conseil du README devenu
nuisible.

Le fil de la session tient en une phrase : **ce qui se voit n'est pas ce qui
s'entend**, et aucun des deux ne se lit dans le code.

## Le mur du MVP est tombé

`app/layout.tsx` n'importait pas seulement du CSS Accor : il importait un fichier
**gitignoré**. Un build depuis le seul dépôt ne pouvait donc pas aboutir, et
c'était le vrai blocage du déploiement — pas la quantité de travail.

`styles/components/` porte désormais les six composants du site, écrits ici :
`.ama-button` (et `.ama-button-icon`), `.ama-chip`, `.ama-input-text`,
`.ama-message`, `.ama-select`, `.ama-skeleton`.

**175 Ko → 19 Ko, versionnés.** L'écart n'est pas un travail de compression, et
c'est ce qui rend la mesure intéressante : le paquet livrait **12 composants dont
6 n'étaient référencés nulle part**, répétait les règles de `button` dans chaque
fichier de composant, et transportait des utilitaires (`.hidden`, `.sm\:flex`…)
que le site n'emploie pas. Des 6 réellement servis, **5 le sont en production** —
`skeleton` n'existe que sur la page kit interne.

`npm run welds:install` n'extrait plus que le thème, dont le seul usage restant
est de servir d'oracle à `tokens:check`. **Le zip WDS devient facultatif pour
faire tourner le site.**

## La leçon la plus chère : six imports valent 1,7 minute

Les six fichiers de composants passent par un `index.css` unique, et le layout
n'importe que lui. Ce détail n'en est pas un.

Importer les six séparément depuis `layout.tsx` faisait **passer la suite de
1,1 à 2,8 minutes et échouer 21 tests**, tous en timeout à 30,0 s sur
`networkidle`, tous en desktop. Aucune assertion n'était fausse : le serveur de
développement recompilait six modules CSS distincts pendant que seize workers
tapaient dessus.

**Joués seuls, ces 21 tests passaient.** C'est ce qui rend le symptôme trompeur,
et c'est la règle que j'en tire : la comparaison qui tranche est **la suite
complète contre la suite complète**, jamais un spec isolé. J'ai conclu deux fois
de travers avant d'y venir — d'abord « cache périmé », puis « vraie régression »
sur la foi d'un `a11y.spec` isolé à 16/16.

## Ce que le lecteur d'écran a montré et qu'aucun outil ne voyait

Sept défauts trouvés à l'usage. **axe-core passait au vert sur chacun.**

| Défaut | Ce qui le causait |
| --- | --- |
| Le libellé du champ annoncé **deux fois** | un `<label>` masqué reste un nœud de texte : lu, puis re-annoncé comme nom du champ |
| Le titre d'article annoncé **deux fois** | le `<title>` reprenait mot pour mot le `h1` |
| Le corps d'article mal cadré | `lang` posé sur 4 000 caractères alors qu'il répétait celui de `<html>` |
| Le focus perdu en quittant le panneau | `autoFocus` s'applique **avant tout effet** ; l'effet capturait donc le champ du panneau et « revenait » dessus en le démontant |
| Le chevron du sélecteur inerte au clic | `mask-image` crée un contexte d'empilement : le `::after` passait **au-dessus** du `<select>` superposé |
| L'ancre « Poser une question » cachant sa cible | la barre est collante ; sans `scroll-margin-top`, l'ancre pose la cible à `top: 0`, donc dessous |
| Le bouton de fermeture à 22 px | largeur déclarée à 24, comprimée par un conteneur flex — sous le plancher WCAG 2.5.8 |

Aucun n'était lisible dans le code sans l'entendre ou l'essayer.

## Trois impossibilités, dites plutôt que contournées

**Détecter un lecteur d'écran n'existe pas.** Aucune API ne l'expose, et les
heuristiques qui circulent — chaîne d'agent utilisateur, `forced-colors` —
relèvent autant du pistage que de l'approximation. La demande « mettre le
carousel en pause quand un lecteur d'écran est actif » a donc reçu la meilleure
approximation disponible, et sous son vrai nom.

**Les raccourcis à touche unique n'atteignent pas un lecteur d'écran**, `?`
compris. La touche est consommée avant que le document ne la voie. Ce n'est pas
contournable côté page : la réponse a dû être **structurelle** — les mêmes
destinations offertes en contrôles réels — et non un correctif de touche.

**Le rectangle bleu ne nous appartient pas.** Il est peint par la technologie
d'assistance par-dessus la page — ici le Narrateur de Windows, dont
`NarratorCursorHighlight` était à 1. Aucun CSS ne peut l'atteindre.

## Le mode de navigation, ou la forme d'un signal

Arthur a demandé si la détection du mode de navigation ne réglerait pas l'arrêt
du carousel. **Non pour la raison qu'on croit** : c'est le même signal, des
événements clavier, pas une détection de lecteur d'écran.

Mais la question visait juste ailleurs. Ma première version posait un **verrou à
sens unique** : une touche, et l'animation était perdue pour de bon, mémorisée.
Un mode est un état **réversible**. L'utilisateur de lecteur d'écran, qui ne
produit aucun événement pointeur, reste en mode clavier toute sa visite ; le
visiteur voyant qui appuie une fois sur `Tab` retrouve l'animation dès qu'il
reprend la souris. Le coût que j'avais fait accepter disparaît.

Trois réglages en découlent, chacun pour une raison écrite : le tactile ne
bascule rien (un lecteur d'écran mobile produit les mêmes `pointerdown` qu'un
doigt), les touches de saisie ne comptent pas, et le bouton lecture prime sur le
mode — sans quoi il serait un contrôle sans effet.

## Les tokens de focus existaient et personne ne s'en servait

`focus.outline-width`, `-offset`, `-style` : trois tokens dans l'export, **zéro
usage**. Douze déclarations écrites en dur les remplaçaient, et le champ de
saisie s'en écartait plus encore — 1 px collé à sa bordure, seul de son espèce.

**`focus-fallback` n'est pas employé, et c'est mesuré.** Le token existe pour les
fonds colorés où le principal manque de contraste ; la palette de ce site n'en
présente aucun. `focus` tient partout, au pire **3,99:1**, quand le repli
tomberait à **2,88:1** sur `surface-alternative` en mode sombre. L'employer par
principe aurait dégradé l'indicateur. Trois paires ont été ajoutées à
`a11y:contrast`, au seuil 3:1 de WCAG 1.4.11, pour le vérifier au lieu de le
supposer.

## Ce que les tests ont appris à faire

**Trois points ne décrivent pas une surface.** Mon premier test de zone cliquable
échantillonnait 8 %, 50 % et 94 % : il **encadrait la zone morte sans jamais la
toucher** — elle allait de 63 % à 83 % — et passait au vert avec le bug dedans.
Il balaye désormais toute la largeur tous les 2 px.

**Playwright n'ouvre jamais une liste native.** `selectOption()` règle la valeur
par programme, un clic sans fenêtre donne le focus sans dérouler. Un test qui
vérifie le focus ou la valeur ne prouve **rien** sur la zone cliquable.

D'où `e2e/audit-a11y.spec.ts` : neuf contrôles, quatre largeurs, trois écrans,
tirés des classes de défauts ci-dessus. Trois retours ont été instruits puis
écartés, **raison écrite** — une tolérance sans raison est une régression
déguisée.

## Deux erreurs de méthode, à ne pas refaire

**J'ai dit « le rendu est inchangé » alors que cinq écarts visuels étaient
passés.** Arthur a dû demander l'inventaire pour l'obtenir. Un changement non
signalé n'est pas un petit changement : c'est un changement que l'autre découvrira
seul, plus tard, sans contexte.

**J'ai conclu trois fois « c'est votre environnement ».** Deux fois à raison, une
fois à tort — et c'est la fois de trop qui coûte, parce qu'elle apprend à ne plus
me croire. Le remède qui a marché : mesurer sur `main` avant de répondre, comme
pour le chevron. Deux minutes, et la réponse au lieu d'une hypothèse.

## La limite de l'outillage, trouvée puis résorbée

Arthur a demandé « on parle de quel champ ? ». La réponse a fait remonter plus
grave que ce que je décrivais : **l'indice de saisie du champ de question**
gardait la couleur par défaut du navigateur, `rgb(117, 117, 117)` — soit
**3,86:1** sur le panneau du lanceur, en 16 px. Sous le seuil AA, sur le champ
que chaque visiteur lit en arrivant.

Et une correction à ce que j'avais annoncé : le champ du héro est concerné **en
permanence**, pas seulement en mode sombre. Son panneau force
`data-color-mode="dark"` puisqu'il est posé sur l'image.

**Pourquoi rien ne l'avait vu.** `a11y:contrast` compare des **paires de tokens
déclarées** : cette couleur n'en était pas une, personne ne l'avait écrite. Le
trou était dans la liste, pas dans le calcul — et une liste ne se complète que
quand on pense à la compléter.

Arthur a ensuite posé la question qui compte : **« as-tu résorbé et documenté
les limites des tests ? »** Non. J'avais corrigé l'instance et ajouté un test
qui ne couvrait que ce champ-là. La classe demeurait.

`audit-a11y.spec.ts` part désormais de l'autre bout : **chaque texte visible de
la page**, sa couleur calculée, et le fond effectif obtenu en composant les
transparences — peu importe d'où viennent les couleurs. 17 textes mesurés sur
l'accueil, 45 sur un article.

Deux ratés instructifs pour détecter « ce texte est sur une image » : chercher un
`background-image` ne suffit pas — les images du site sont des balises `<img>`,
et le titre du héro ressortait à **1,00:1** ; `elementsFromPoint` non plus —
c'est un test de **pointeur**, qui ignore ce qui est en `pointer-events: none`,
précisément le calque de texte du héro.

## APCA, et un invariant qui tient

L'article de Kortic recommande de calculer les deux algorithmes en parallèle
tant que WCAG 3 n'est pas ratifié. Fait — sans jamais bloquer la commande.

**Le résultat vaut le détour** : les thèmes sont obtenus par rotation de teinte à
luminance relative *WCAG 2* constante, et rien ne garantissait que la promesse
tienne pour APCA, qui n'a ni la même fonction de transfert ni le même modèle.
Mesuré : **0,8 d'écart de Lc au pire** entre les trois personas. La garantie du
README vaut donc au-delà de l'algorithme pour lequel elle avait été conçue.

APCA a aussi montré ce que le ratio masque : le texte saisi donnait **Lc −53**
pour 7,26:1. Le ratio est symétrique, la perception ne l'est pas, et le mode
sombre est là où il flatte le plus. Le texte est passé à `on-surface-mid`.

## La documentation, qui disait le contraire de ce qu'il faut

Le README conseillait, pour diagnostiquer une vague de timeouts, de vider
`.next` puis de relancer la suite. **Ce geste provoque désormais l'échec qu'il
prétend écarter** : le premier run paie la compilation de `/articles/[slug]`
pendant que seize workers tapent dessus.

Le symptôme a donc trois causes, dont deux sont l'inverse l'une de l'autre —
cache périmé, cache vide, et trop de modules CSS importés depuis le layout. La
section les décrit toutes les trois, donne la séquence avec **préchauffage**, et
rappelle la règle qui vaut pour les trois : la comparaison qui tranche est la
suite complète contre la suite complète.

Une incohérence du même ordre a été corrigée : **`npm run a11y` documentait un
audit qu'il ne lançait pas**. Il enchaîne désormais les trois contrôles —
contraste, axe-core, audit systématique — soit 188 tests.

Une documentation qui a pris du retard n'est pas neutre : elle **coûte** plus
que son absence, parce qu'on la suit.

## Reste à faire

- **Le texte saisi reste à Lc −53 en indice de saisie**, sous le seuil APCA d'un
  texte courant. Conforme AA (7,26:1), donc laissé tel quel : APCA n'est pas
  ratifié et la hiérarchie visuelle entre indice et texte saisi a sa raison
  d'être. À revoir le jour où WCAG 3 le devient.
- **`/dev/kit` n'a ni `main` ni repère** : le lien d'évitement qu'il recevait du
  layout pointait vers un `#contenu` inexistant. Page interne, hors périmètre
  d'audit, mais l'incohérence est là.
- **MVP** : rate limiting Upstash sur `/api/chat` — la route n'a **aucune limite
  par IP** et la clé API est à la merci du premier script venu —, puis SEO/OG,
  analytics, déploiement Vercel et domaine.
- **Faire les passes au lecteur d'écran sur un build de production** : en
  développement, Next.js injecte sa surcouche d'outils, un arrêt de tabulation
  supplémentaire et un logo « N » qui n'existent pas en production.
