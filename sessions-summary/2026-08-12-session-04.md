# Session 04 — 2026-08-12 : audit d'accessibilité WCAG 2.2 AA

Audit complet de l'accueil, des pages articles et du panneau de conversation,
sur 3 personas, 2 modes et 4 largeurs. Treize constats, tous corrigés. Livré
sur `feat/a11y-audit` → **PR #14**, empilée sur `feat/nav-footer` (#13) qui
touche les mêmes fichiers.

Le rapport lui-même vit dans `docs/accessibilite.md` : constats, ce que le
lecteur d'écran annonce à chaque parcours, non-défauts vérifiés, procédure
manuelle.

## Le point de départ

Deux remarques d'Arthur, toutes deux exactes :

- l'`aria-label` du champ de saisie recopiait son placeholder ;
- « Lire l'article » n'était pas interactif et le nom du lien de card
  concaténait tout son contenu, surtitre en tête.

La lecture du code en a sorti onze autres, dont trois bloquantes.

## Ce qu'il faut retenir

- **Le fil du chat était lui-même la région `aria-live`.** Le texte y arrivant
  token par token, le paragraphe entier était ré-annoncé à chaque insertion :
  inutilisable au lecteur d'écran pendant la génération. Une région
  `role="status"` hors écran le remplace, avec deux valeurs par échange.
  C'est le piège classique du streaming, et il ne se voit qu'à l'oreille.
- **`aria-label` est ignoré sur un élément générique.** Le groupe de questions
  suggérées n'avait donc aucun nom, alors que l'attribut était bien là.
- **Un `<select>` en `opacity: 0` emporte l'anneau de focus avec lui.** Les
  chips de réglage ne montraient rien au clavier. Corrigé par
  `:has(.site-nav__select:focus-visible)` sur le chip.
- **Le panneau est passé en portail sur `<body>`.** Il était rendu dans
  `<main>` : impossible de rendre le contenu inerte sans s'inerter soi-même.
  Étant en position fixe, le rendu ne change pas d'un pixel.
- **`prefers-reduced-motion` ne se règle pas en CSS pour les défilements
  JavaScript** : `behavior: "smooth"` est une valeur passée à une API, aucune
  media query ne la neutralise. D'où `lib/motion.ts`.

## Sur la valeur du balayage automatique

Mesuré, pas supposé : lancé sur le code d'avant correction avec les règles
WCAG, **axe-core ne signalait aucune des treize anomalies** — 42 règles
passées, zéro violation. Avec la famille `best-practice` il en attrapait une
(le saut `h1` → `h3`) et en signalait une seconde « à vérifier ». Les onze
autres viennent de la lecture du code et du dépouillement de l'arbre
d'accessibilité du navigateur (`locator.ariaSnapshot()`), qui a d'ailleurs
révélé un doublon vocal non prévu : le libellé visible du chip répétait la
valeur du `<select>`.

Le balayage ferme la porte aux régressions mécaniques. Il ne remplace ni la
lecture du code, ni la passe manuelle — c'est dit tel quel dans le README et
dans le document d'audit, pour que personne ne s'y fie seul.

## Incidents gérés

- **Un test de navigation échouait une fois sur trois** sur la suite complète,
  jamais isolément. Diagnostiqué : sous charge parallèle des quatre projets, le
  serveur de développement compile la route cible à la demande et le délai de
  5 s expirait sur une navigation pourtant en vol — l'URL reçue était encore
  l'ancienne. Marge portée à 15 s sur les trois assertions de navigation, deux
  passages complets consécutifs au vert. Ce n'était pas un clic perdu, et le
  mettre sur le compte du hasard aurait laissé la suite instable.
- **Le premier test de garde écrit pour le pied de page ne gardait rien** :
  vérifié en retirant le correctif, il restait au vert. Durci puis re-vérifié
  dans les deux sens. Vaut pour tout test de non-régression écrit après coup.

## Vérifications

- 212 tests Playwright sur 4 largeurs, dont 48 d'accessibilité (`npm run a11y`).
- `npm run a11y:contrast` : AA sur 3 personas × 2 modes.
- Arbre d'accessibilité relevé et consigné dans le document d'audit.
